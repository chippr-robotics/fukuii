# SNAP Sync Routing Protocol (DRAFT — spec 016)

Where each SNAP phase lives, what configures and measures it, how it logs, and who reviews changes to it. Use this
doc to point an agent at **one** phase without having it read the 6,646-line controller.

Used by: all agents touching `blockchain/sync/snap/`. The primary reviewers are named per row.

Spec: `specs/016-snap-controller-split/` (#1401). Phase 0 data: `specs/016-snap-controller-split/research.md`.
State capabilities and execution witnesses: `specs/017-state-capabilities-witnesses/` (stub; depends on T055).

**Status of this doc**: **draft**. Rows marked **current** point at today's code (`staging@9a6681cc0`; line numbers
moved when PR #1501 merged on 2026-10-08, so search by symbol; post-#1501 anchors are in research.md R1). Each spec-016 slice flips its rows to **target (post-split)**, with the
real file names, in the same PR. Slice R1 (T090) checks every row with grep.

Paths are relative to `src/main/scala/com/chipprbots/ethereum/blockchain/sync/snap/` unless they start with
`network/` or `src/`. `SSC` = `SNAPSyncController.scala`. Config keys are under `sync.snap-sync.` (`base/sync.conf`)
unless stated.

## Rules that apply to every row

- **On-disk formats are frozen during the split**: the progress string, `SnapSyncProgressStorage` (ns `p`),
  `AccountResumeCheckpoint` v1, the storage/codeHash task files, `SnapStorageDone/` markers, `HealingFrontierStorage`
  (CF `g`), `BfsQueueStorage`, the AppState phase flags and `snap-good-peers.v1`. Any change to them needs **vault**
  plus its own spec.
- **No bug fixes in move PRs.** Fixes are their own PRs against the current layout (spec 016 NG-4).
- **ETC and ETH share this code.** The split is by phase, not by chain. Hash scheme = ETC/Mordor; Path scheme and the
  CL pivot hint = ETH/Sepolia. ETC-reachable behaviour changes need **forge**; CL-pivot and Path-scheme changes need
  **beacon**.
- **Do not route SNAP work to `loom`.** The SNAP actors are already Pekko Typed.
- **State capability boundary (spec 016 amendment 2026-10-11; spec 017).** SNAP code reaches storage only through
  **`StateIngest`** (from T055): bulk trie-range/node writes with no execution, plus SNAP's verification reads (proof
  checks, healing presence checks, state validation, publish verification). SNAP code **never holds `StateAccess`**,
  the EVM-execution capability of spec 017. The dependency check for this is delivered by spec 017 (DC-4); it will
  extend the T054 ratchet tooling, and it is vacuous until `StateAccess` exists. A relaxed durability policy (for
  example a lighter WAL, T056) may be set on `StateIngest` only. **The exporter is the durability boundary:** the
  `PathToHashExporter` publish (Path scheme) and the explicit flush/sync barrier before `completeSnapSync` (Hash
  scheme) always run at full durability, before SNAP is marked complete and before execution reads the store
  (FR-044). Changes there need **vault** plus **forge** (Hash) or **beacon** (Path).
- **Env freeze ratchet (T054, PR #1570).** `scripts/snap-split/verify.py` step 8 checks the PR head against
  `scripts/snap-split/storage-baseline.json`: the `SnapControllerEnv` member count (18) only goes down, and so does
  the storage-reference **total** (storage-type identifiers and storage member accesses, comments excluded) over
  `snap/controller/`, `snap/actors/` and the core `SNAPSyncController.scala` (since T054c: the split's move source,
  so a move out of the core is a per-file trade); per-file counts may move between files. Calls on `StateIngest` are not
  storage references. A PR that lowers a count records it in the baseline in the same PR. The coordinator stage pays
  the table down. T055 runs under the T054b verify mode.
- **Capability mode (T054b).** A behaviour-neutral PR that introduces a capability and moves call sites onto it (T055,
  `StateIngest`) is neither a move nor a narrowing. It is selected by the commit trailer `# capability: <Trait>`, on a
  `refactor/snap-016-*` branch only. Once one commit of a PR carries it, every commit that touches a `src/main` file
  under `snap/` must carry it, and no commit may be a move (`# moved:`) or a narrowing. A PR that removes a pinned
  `SnapControllerEnv` storage handle must be a capability PR. In a capability commit:
  - the capability file is the one file under `snap/controller` or `snap/actors` that declares `trait <Trait>` at the
    top level; the accessor is the trait name in lower camel case (`stateIngest`);
  - the file declares the call-site map in comment lines, `// capability-map: <handle>[.<member>...] -> <member>`. The
    handle is a pinned env storage member or a name the ratchet counts as a storage reference; the member is declared
    in the trait. The production implementation lives in the same file, and each mapped member is a pure forwarder:
    its body is the left side applied to its own parameters in order, with no default parameters (it may read the
    handle under the member name a bare `handle -> member` line gives it). A mapped handle is only wired in
    (constructor parameter or abstract member), never defined in the file;
  - the capability file has a fixed shape, checked on every capability commit and, after the capability exists, at the
    head of every PR. It holds package and imports, `trait <Trait>:` with abstract `def`/`val` members only, and
    `object <Trait>:` holding only `enum`s of plain `case` lines, `type` aliases, one
    `def apply(<params, no defaults>): <Trait> = new <Prod>(<its params, by name, in order>)`, and one
    `class <Prod>(<the same params>) extends <Trait>`. That class's body holds only forwarder `def`s of mapped members.
    A member that is not forwarded (a handle under its member name, or a policy such as `durability`) is a `val`
    constructor parameter, never a body `val` with an initializer. Nothing else is allowed: no statements, no extra
    objects or classes, no unmapped `def` with a body, and no declaration sharing a line (`;`) with another;
  - every change to another `.scala` file under `snap/` is checked at token level over the whole file: only mapped
    substitutions (`<handle>[.<member>]` becomes `<accessor>.<member>`), comment and whitespace changes, and named
    (not wildcard or `given`) imports. Statement lines keep their position and indentation; an argument list may be
    re-wrapped, and a single-expression body may join its `=` line. Interpolated `${...}` code is checked like other
    code;
  - `SnapControllerEnv` may only lose pinned storage handles and gain the accessor, declared `: <Trait>`. The core
    `SNAPSyncController.scala` may add one accessor declaration, `<Trait>(a1, ..., an)`, with one argument per
    `apply` parameter in order. The i-th argument is the handle bare-mapped to that parameter (or the handle with the
    parameter's name), or, for a parameter typed by a declared enum, one of its cases
    (`StateIngest.Durability.Default`). A named argument must name the parameter. A module's `<X>State` may drop a
    storage-typed abstract member. A dropped or added declaration must stand alone on its lines. No other file may be
    added or deleted, and no `src/main` file outside `snap/` may change;
  - `ChildFactories` signatures do not change: spawn sites pass `stateIngest.<handle>` to the existing handle parameters.
    (`ChildFactoriesSpec`, a protected pin, compares each method's default positions with the child's `apply`.)
  Rule (a), rule (d), `[counts]`, the test-hunk guard, pin and golden protection and step 8 still apply. In step 8, the
  capability has a `capabilities` row in `storage-baseline.json` (file, member count, raw imports), recorded in the PR
  that introduces it. The member count only goes down unless a justification line is added. The raw-import list is
  fixed at introduction and only shrinks. The capability file is not a `storage_refs` row. Elsewhere,
  `<accessor>.<call>` is not a storage reference, while `<accessor>.<handle>` (a parameterless storage-typed member)
  counts once. In a capability PR, removed env handles must also leave `env.storage_members`.
  - **Test files.** A capability commit edits tests under the same test-hunk guard as any refactor commit (S0f, step 3).
    Lines with an assertion or scheduling token may not be added or removed, while other lines (fixtures, a new
    `val`) may. That is the guard's intent, unchanged by T054b.
  - **What the gate cannot check (review covers it):** types, and that every trait member is implemented (the compiler
    does both); what a test-file fixture edit means; and the semantics of the storage classes' own methods, which
    are outside `snap/` and so cannot change in the PR. After the capability PR, the core's accessor declaration is
    ordinary core code: a later PR that edits it is checked only by that PR's own mode (move, narrowing or fix). The
    PR-head re-check of an existing capability file checks its shape and its forwarders, but not that each map root
    is a pinned handle, because the pinned list is empty after T055.
- **No sbt on the soak host.** CI is the compiler.
- **Module form (ADR CON-013).** Every module is a trait whose self-type is
  `<Module>State & <capabilities> & <Callee>Api…`. A module file never mentions `SNAPSyncControllerImpl` or a
  `*CoordinatorImpl`. To change what a module touches, change its `<Module>State` or Api traits, and update the
  counts below in the same PR. A count must not grow without a justification line. `scripts/snap-split/verify.sh`
  (S0f) checks this, and so does the required CI job `snap-split-verify`.
- **CI reality.** Staging PRs run Tier 1 only (`testEssential`, which excludes `SyncTest`). `SyncControllerSpec`,
  `PivotHeaderBootstrapSpec` and `SnapServingActorSpec` run only in the `snap-synctest` job (S0e). That job runs on
  every PR to staging, exits early when nothing under sync changed, and checks the JUnit reports against a one-entry
  allow-list: task #68, `SyncControllerSpec:762`. It fails if #68 passes or is missing. One re-run of a
  non-allow-listed failure is allowed (FR-039).
