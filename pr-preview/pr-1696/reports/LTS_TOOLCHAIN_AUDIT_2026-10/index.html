    2. Scala: what the 3.3 → 3.9 LTS move involves¶

    Facts from the 3.9 announcement (scala-lang.org/news/3.9, read 2026-10-17):

    • 3.9 LTS is guaranteed maintenance for at least three years. 3.3 LTS is maintained for one year after 3.9.0, "future backports are expected to be fewer". Staying on 3.3 is safe until about 2027-09 and then is not.
    • Minimum JDK 17. fukuii is on 25: no change.
    • Artifacts built with 3.9 cannot be consumed by 3.3 projects. fukuii publishes bytes, crypto and rlp; all modules move together, and anything downstream that consumes them on 3.3 breaks. The vendored scalanet modules are compiled in-tree and follow.
    • Recommended order: build tool, JDK, Scala, then libraries. Compiler rewrites: apply -source:3.4-migration through -source:3.9-migration, each with -rewrite, one step at a time, committing after each; later flags do not replay earlier patches. Some changes have no rewrite.
    • Given prioritization changed in 3.7 (the most general matching instance wins). -source:3.5 keeps the old rules; -source:3.7-migration warns where they differ. This intersects the repo's own given/using migration (.claude/agent-protocols/scala3-given-migration.md, P3a done, P3b pending): finish P3b before, or fold it into, the 3.9 migration so the prioritization change is reviewed once.
    • Implicits from inaccessible companions warn under -deprecation in 3.9 and stop resolving in 3.10. fukuii compiles with -deprecation; new warnings land in the warning ratchet.

    Things in build.sbt to re-verify against the 3.9 compiler during the migration, because the announcement does not cover them: -source:future (the repo relies on it for import x.* enforcement), -Ykind-projector (a -Y flag; confirm it is still accepted or has moved), -Wconf:id=E198:error (message ids can renumber between minors), -Xmax-inlines:64, and the -language:adhocExtensions suppression.

    Toolchain that must move with it: scalafmt 3.8.3 → 3.11.x (the scala3 dialect must parse 3.9 syntax; the constitution's text names 3.8.3, so a PATCH amendment accompanies the bump), sbt-scalafix 0.13.0 → 0.14.9, sbt-scoverage 2.2.2 → 2.4.4, semanticdbVersion (follows scalafixSemanticdb.revision).

    Why it matters for the roadmap specs: spec 017, 018 and 019 all add new code, and spec 019's Approach B reads TASTy. TASTy format follows the compiler minor; a translator written against 3.3's TASTy is rewritten for 3.9's. The cheapest sequence is migrate before 017 starts: after spec 016's remaining slices (which are byte-moves and should not straddle a compiler change), as its own spec, and before any 017 code lands. Recommendation R-1.

    3. sbt¶

    • 1.x: 1.10.7 → 1.12.15 is a drop-in bump (same plugin ABI _2.12_1.0). 1.13.0 exists on Maven Central (2026-08-20); take it only after reading its notes. The dependency-check.yml and CI "Set up SBT" steps follow build.properties.

    4. JVM¶

    JDK 25 is the current LTS and the repo is on it everywhere that matters: every workflow (java-version: '25', Temurin), every Docker builder and runtime image (eclipse-temurin:25-*-noble), the distroless runtime (gcr.io/distroless/java25-debian13), and the release notes ("requires JDK 25+"). The floating 25 tags pick up Temurin patches (25.0.4.1+1 as of 2026-08-19) without a repo change. JDK 26 and 27 are feature releases, not LTS; the next LTS is 29 in September 2027. Spec 018's FFM route needs java.lang.foreign, final since JDK 22, so 25 covers it.

    Documentation drift: docs/adr/infrastructure/INF-001-scala-3-migration.md is titled "Migration to Scala 3 and JDK 21" and docs/adr/README.md, docs/adr/infrastructure/README.md, INF-002, INF-003 and docs/adr/MIGRATION_GUIDE.md still say JDK 21. The constitution and CLAUDE.md say JDK 25. Recommendation R-6.

    6. Recommendations¶

    • R-1 (spec-required, sequence it before spec 017; stubbed as specs/020-scala-3-9-lts-migration/). Scala 3.3.8 → 3.9.x LTS as its own spec: build tool first (R-2), then the compiler with the -source:3.4-migration … -source:3.9-migration rewrites one step per commit, then scalafmt 3.11.x / sbt-scalafix 0.14.9 / sbt-scoverage 2.4.4, then libraries. Fold the pending P3b given migration into it. Gate on testEssential, testStandard with coverage, ethereum/tests on both chains, and the rpc-compat and graphql inertness oracles. Amend the constitution's scalafmt version (PATCH). Spec 019's TASTy translator and spec 018's bake-off harness then target one toolchain.
    • R-2 (zero-risk, now). sbt.version = 1.12.15; plugin bumps on the sbt 1 line: sbt-scalafmt 2.6.2, sbt-scalafix 0.14.9, sbt-scoverage 2.4.4, sbt-native-packager 1.13.0, sbt-assembly 2.5.0, sbt-buildinfo 0.13.2, sbt-ci-release 1.12.1, sbt-git 2.2.0, sbt-updates 0.7.1, sbt-api-mappings 3.1.0, sbt-kanela-runner 2.1.1, and sbt-javaagent moved to com.github.sbt 0.3.0. One PR, sbt pp green. (sbt-scalafix 0.14.x may need the scalafix rules' pins checked.)
    • R-3 (spec-required, later). sbt 2.0.x after R-1, and only once sbt-kanela-runner and sbt-scapegoat have sbt 2 builds or are replaced; sbt-git's sbt 2 build is an RC. Review ThisBuild/bare-settings semantics and the it, evm, rpcTest, benchmark configurations.
    • R-4 (low-risk batch). The patch/minor table in §5, one PR, testEssential once; netty 4.1.139 in the same batch.
    • R-5 (evaluate). pekko 1.7.1, pekko-http 1.4.2, cats-effect 3.7.1, fs2 3.14.0 together, with testEssential and the SNAP SyncTest job; loom reads the Pekko notes.
    • R-6 (docs). Replace "JDK 21" with 25 in the ADR index, INF-001/002/003 and the migration guide, or add a note that INF-001 records the historical target.
    • R-7 (CI). Add sbt dependencyUpdates to dependency-check.yml beside dependencyTree, so the weekly artifact carries the list this audit had to assemble by hand.
