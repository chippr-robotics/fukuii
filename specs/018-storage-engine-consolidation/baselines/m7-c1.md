# M7 after C1: what the trie change costs on the hash-keyed store (T033)

**Status: the stand-in is recorded; the merge gate itself is open.** T033 asks for `[IMPORT-TIMING]` and the allocation rate
(JFR) of an import of the recorded Mordor range, with the pinned jar and with the C1 branch. Neither the pinned jar (T002) nor the
recorded range (T003, T004) exists yet, and the session that built C1 ran in a cloud container with no chain data. What is
recorded here is the same comparison in the small: bytes allocated per trie operation, parent commit against C1, on the store both
chains run on today.

## How it was measured

`src/benchmark/scala/com/chipprbots/ethereum/mpt/TrieAllocationBenchmark.scala`, added in the C1 PR. It uses the trie's public API
only, so the same file runs on either side of the change:

```
sbt "Benchmark / testOnly *TrieAllocationBenchmark"
```

- A trie of 50,000 keys (`keccak256` of a counter, 70-byte values) over `SerializingMptStorage` on `ArchiveNodeStorage` on
  `EphemDataSource`, with no decoded-node cache in front, so every node on a path is read and decoded.
- 5,000 operations of each kind, measured with `ThreadMXBean.getThreadAllocatedBytes` for the calling thread (the idiom of
  spec 007), after two warm-up rounds. Two measured rounds, which agree to within 13 bytes per operation.
- JDK 21.0.12, Linux x86_64, 4 cores. Parent: staging `a69b0d7ae` (0.11.44), in a separate clone.

## Result (bytes allocated per operation)

| Operation | Parent `a69b0d7ae` | C1 | Change |
| --- | ---: | ---: | ---: |
| put (new key) | 66,776 | 66,210 | -566 (-0.8 %) |
| put (key already there) | 69,055 | 68,586 | -469 (-0.7 %) |
| get | 50,002 | 50,435 | +433 (+0.9 %) |
| remove | 66,858 | 66,628 | -230 (-0.3 %) |

So the position each node is read at and reported at costs less than one percent of what the trie allocates per operation, in
either direction. The read path gains a little: the path a lookup has walked used to be built for the missing-node message only,
and is now also handed to the storage. The write paths lose a little, by reusing one `ByteString` in the leaf split.

## What this does and does not show

- It is the hash-keyed store, which is the only store in use until C3b. The position-keyed side (`collapseTrieAt`,
  `TriePosition`) is not in this figure: nothing in production calls it yet, and its cost is measured in C3b (M8) and at the gate.
- It is allocation, not time. It says nothing about `[IMPORT-TIMING]`.
- It reads every node from the store. With the decoded-node cache in front, as block execution has it, the absolute figures are
  smaller and the same few hundred bytes are a larger share of them. That is what the real M7 measures.
- It also shows where the bytes go today: a lookup of one key allocates about 50 KB, most of it decoding each node on the path
  twice (`MerklePatriciaTrie.getFromHash` decodes what the storage already decoded). That is older than this track and is not
  changed here.

**The gate stays open:** T033 is not ticked. It is run when T002 and T004 exist, on the Mordor range, against the spec 007 budget.
